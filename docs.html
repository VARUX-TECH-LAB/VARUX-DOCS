What AXIS is

AXIS is a deterministic control layer for PostgreSQL write paths. It sits between applications, operators, scripts or AI agents and the database, classifies SQL, evaluates versioned policy, enforces the decision, and records durable audit evidence. The current package is designed for local technical review and pilot planning; it shows how the core enforcement, audit, approval, visibility, and policy lifecycle pieces fit together.

AXIS is

  • — deterministic PostgreSQL write-path control
  • — a controlled execution gateway (Gate)
  • — a policy-enforced decision layer
  • — an approval boundary for risky operations
  • — a durable audit evidence generator
  • — an operator visibility and policy lifecycle surface

AXIS is not

  • — WAF, SIEM, or DLP
  • — SQL injection detector
  • — masking/encryption product
  • — query optimizer
  • — full drop-in PostgreSQL wire-protocol proxy
  • — PgBouncer / connection pooler replacement
  • — replacement for application authorization
  • — a guarantee that "ALLOW" means the operation is semantically safe
  • — compliance-certified release

01 · Quickstart

Run AXIS locally for review

The local stack is the reviewer path: Docker Compose starts AXIS and a bundled PostgreSQL. All evidence and audit files stay local. This is reviewer packaging, not a production deployment guide.

Prerequisites

Windows: Git, Rust toolchain from rustup, Docker Desktop, Node.js LTS, npm. Linux/macOS: Git, Rust toolchain, Docker and Docker Compose, Node.js LTS, npm. Python 3.10+ is needed for the verification scripts.

Start the backend

git clone <repository-url>
cd AXIS

# static and test checks first
cargo fmt --check
cargo check
cargo test

# local stack: AXIS + bundled PostgreSQL
docker compose up --build

# AXIS:  http://localhost:6543 (HTTP gate)
# PostgreSQL: localhost:5432

To run the Rust service directly instead of Docker (PostgreSQL must already be reachable): cargo run.

Control plane

cd control-plane
npm install
npm run build
npm run dev
# open http://localhost:3000

The control plane proxies browser requests through /api/axis/... to the server-side AXIS_BACKEND_URL (default http://localhost:6543). Browsers must not call the backend directly.

Enforcement outcomes

200 ALLOW403 BLOCK202 REQUIRE_APPROVAL plus controlled 4xx/5xx failures with structured error metadata (error.code, category, severity, safe_to_retry, operator_action).

Policy lifecycle endpoints

POST /policy/validate, POST /policy/diff, POST /policy/dry-run (never executes, never writes audit evidence, never creates approvals), POST /policy/candidates, POST /policy/activate and POST /policy/rollback (the last three require the operator token when configured).

Audit corruption or an unwritable audit path is never silently repaired. AXIS reports it. If /evidence/verify reports invalid records, investigate before continuing — do not delete evidence from any reviewer, pilot, or shared environment.
02 · Architecture

Deterministic write-path architecture

The execution path is: Gate → Context Builder → SQL Classifier → Policy Engine → Approval Workflow → Audit/Evidence Store. Every protected write produces context, a decision, and evidence — in that order.

ClientsApps / scripts / AI agents / operators
▼
GateRequest validation · Context Builder
SQL ClassifierParse · normalize · fingerprint · operation · scope · risk signals
▼
Policy EngineVersioned deterministic evaluation
▼
DecisionALLOW → execute through PostgreSQL, then record result evidence
DecisionBLOCK → evidence written, zero execution
DecisionREQUIRE_APPROVAL → approval record + evidence, no execution until resolved
▼
Audit / Evidence StoreCanonical WAL · JSONL projection · hash chain · derived index
Decisions are deterministic: the same request context under the same policy_version produces the same decision. AXIS does not guess with AI — policy decides, classification is the single source of truth for authorization (Security Classification Contract v1.0, locked 2026-08-07).

Core components (from the architecture record)

  • Listener/API layer — Axum HTTP service exposing /query, approvals, audit, runtime, evidence, and policy lifecycle endpoints.
  • SQL classification — PostgreSQL SQL parsing, normalization, fingerprinting, operation detection, target extraction, scope estimation, risk signals.
  • Session store — in-memory session_id-scoped prepared statement metadata for AXIS-side PREPARE / EXECUTE / DEALLOCATE enforcement.
  • Policy engine — versioned policy evaluation producing ALLOW, BLOCK, or REQUIRE_APPROVAL.
  • Approval store — SQLite-backed approval state machine (documented historically as JSONL): pending and resolved records.
  • Audit logger — WAL plus JSONL projection with event hashes and previous-hash linkage; derived audit index as a disposable read model.
  • Evidence verifier — read-only hash-chain verification (GET /evidence/verify, GET /audit/verify).
  • Runtime log store — bounded in-memory operational log buffer exposed by GET /logs; visibility only, not evidence.
  • Policy lifecycle store — immutable local version files, active pointer, candidate state, validation, activation, rollback; manifest-based startup.
  • Runtime visibility endpoints — health, runtime stats/metrics, logs, audit explorer, policy status, evidence verification.
  • Control plane — Next.js operator surface (see below).
  • Native pgwire lab listener — disabled by default; Simple Query interception plus extended-query driver flows (see ORM section).

Prepared statement fail-safety (HTTP gate)

AXIS-side PREPARE validates the inner SQL, registers session metadata, writes audit evidence, and does not forward a database-side PREPARE. EXECUTE resolves the stored original SQL and evaluates it through policy; an unresolved, cross-session, malformed, or missing-session EXECUTE never becomes a silent ALLOW. Allowed prepared EXECUTE is not blindly forwarded as raw PostgreSQL EXECUTE, because HTTP sessions do not guarantee pooled backend connection affinity.

Policy lifecycle and manifest startup

  1. Startup: verify audit WAL continuity → load and validate policy manifest → resolve and hash active policy file → parse and validate policy model → run deterministic activation dry-run corpus → write lifecycle audit events → accept traffic.
  2. Candidate policies are validated before storage; diff compares candidate vs active; dry-run reuses classifier and policy evaluation without SQL execution, audit writes, or approval creation.
  3. Activation requires the candidate ID + expected_hash, re-validates, then swaps the in-memory active policy. Rollback requires a valid stored version + expected hash. Old versions are retained; no silent policy downgrade.

Native PostgreSQL wire mode (lab)

The lab listener (AXIS_PGWIRE_ENABLED, default false, port 6544) performs cleartext startup/auth pass-through in lab mode, intercepts Simple Query (Q) messages, maps them into the existing AXIS policy model, and returns PostgreSQL-compatible ErrorResponse for blocked, approval-required, unsupported, backend-failed, policy-failed and audit-failed paths. BLOCK and APPROVAL_REQUIRED send zero original query bytes to the backend — proven at byte level with a backend mock, not by empty PostgreSQL logs. Extended-query driver flows (parameterized statements through Parse/Bind/Execute before Sync) are exercised by real-driver tests; same-cycle pipelining is rejected (SQLSTATE 42501). COPY and the CopyData sub-protocol are fail-closed. CancelRequest is implemented and audited (RFC-032, 2026-07-10).

This lab PoC is not production-ready, not enterprise pilot-ready, not ORM-compatible as a universal claim, and not a "complete PostgreSQL proxy". Unsupported protocol paths fail closed.

Control Plane (operator surface)

Views

  • Dashboard — health, runtime status, integrity, recent activity
  • Query console — direct /query evaluation
  • Approval center — pending approvals and resolution
  • Evidence explorer — recent audit events, event detail, decision trace
  • Policy lifecycle — validate, diff, dry-run, versions, activate, rollback
  • Runtime — service status, audit posture, limits, evidence verification
  • Logs — real runtime logs from /api/axis/logs

Honesty rules

  • real mode shows live backend state; mock mode is explicit server-side demo behavior only, never production evidence.
  • Runtime log entries never expose raw audit WAL records, raw headers, DB credentials, operator tokens, backend URLs, or raw SQL bodies.
  • Decision counts shown are derived from recorded audit decisions, not synthetic counters.
  • Operator token is injected server-side; browser code never receives it.

03 · Security Model

Enforcement, fail-closed behavior, and transport status

The security model is a local hardened security core, not an enterprise product. What is actually implemented today — and what is still missing — is stated explicitly below.

Policy model (current baseline policy policies/prod_main.json)

SQL classDefault policy behavior
ReadsDefault ALLOW
WritesDefault BLOCK
DDLDefault REQUIRE_APPROVAL
Specific single-row orders updatesCan be allowed for allowed webapp roles
Bulk updatesREQUIRE_APPROVAL
Deletes without WHEREBLOCK (risk signal delete_without_where)
Selected migration cleanup pathsREQUIRE_APPROVAL with a different approver group

Operating modes

shadow (records policy result, allows execution) · approval_first (can force high-risk writes to approval) · enforce (applies decisions) · emergency_bypass (can allow blocked write paths with audit evidence). The current hardening evidence uses enforce.

Classifier and parser controls (implemented)

Request controls

  • Empty SQL rejection
  • Multiple-statement rejection
  • Parser errors → controlled request rejection
  • Unsupported statement types rejected
  • Write-like or locking read forms rejected (incl. selected CTE and SELECT INTO patterns)
  • SQL normalization and fingerprinting for audit evidence
  • Scope estimation for single-row vs batch write behavior

Risk signals

prod_write · ddl_operation · bulk_operation · delete_without_where · unknown_target · unknown_scope · cross_schema.

Under the Security Classification Contract v1.0 (locked 2026-08-07), classification is the primary control ("Semantic > Syntax", "State Mutation = Write", fail-closed on ambiguity); risk signals are a fallback override for defense in depth, never the primary protection. Mandatory write patterns include INSERT/UPDATE/DELETE, SELECT INTO, CREATE TABLE AS, MERGE, TRUNCATE, DROP/ALTER, REFRESH MATERIALIZED VIEW, COPY FROM, CALL, DO, nextval()/setval(), lo_import/lo_export, and data-modifying CTEs. COPY TO PROGRAM and ALTER SYSTEM are critical — always BLOCK.

Approval model (implemented)

  • REQUIRE_APPROVAL creates a pending approval record; the original query is not executed when the record is created.
  • Resolution can approve or reject; approved requests execute only after audit writability is checked; rejected requests are blocked.
  • Already-resolved approvals cannot be resolved again; the concurrent approval race test verified one approval cannot produce multiple final executions in the tested local baseline.
  • Approvals never hold database transactions, locks, or TCP sockets open while waiting for a human. In pgwire mode inside a transaction, BLOCK/APPROVAL_REQUIRED poisons the session, issues an audited policy-exempt safety ROLLBACK, and closes the connection (strict v1.2 default).
  • Human wait time is never counted in approval latency measurements.

Transport and identity status — what is really done vs missing

Implemented today

  • Deterministic pre-execution enforcement with fail-closed rejection
  • Policy manifest + SHA-256 local file integrity at startup (v0.9)
  • Operator token (X-AXIS-Operator-Token / Bearer) for mutating lifecycle and approval endpoints; production profile fails fast on weak tokens
  • Rate limiting, bounded timeouts, body/SQL size limits, pool bounds
  • Optional JWT HS256 enterprise demo mode (AXIS_AUTH_MODE): actor/tenant/role derived from a verified token instead of spoofable JSON fields — documented as local/demo auth, not enterprise IAM
  • pg_hba baseline checks and drift detection are specified in the hardening notes (AXIS_PG_HBA_*); signed audit WAL and checkpoint anchoring are described in hardening notes as implemented paths (axis-audit-verify, epochs.log, axis.audit.checkpoint.v1)

Not implemented yet

  • TLS/mTLS on the pgwire transport. As of RFC-032 (2026-07-10, the newest dated evidence): client-to-AXIS SSLRequest receives N in lab mode or is rejected when lab mode is disabled; the backend forwarder opens a raw TCP stream; no TLS mode, CA, cert, server-name, rustls or native-tls configuration exists on either normal or CancelRequest paths. Cleartext traffic is restricted to loopback / isolated container network / protected private overlay. Deploying the current pgwire transport across an untrusted network is not supported.
  • HTTP gate TLS. The v1 security core documented as "no auth, TLS, or RBAC"; TLS/mTLS configuration surfaces (AXIS_TLS_*, upstream mTLS variables) are specified in the hardening notes for production-mode hardening.
  • Identity: request identity fields (actor, app, tenant, role, host, env) are evidence and policy inputs, not verified identity claims. Approvers are not authenticated; the actor in approval resolution is recorded, not cryptographically verified.
  • Full RBAC / SSO; KMS / HSM-backed key management; OIDC/JWKS production identity integration
  • External tamper-proof audit ledger; distributed audit chain across multiple AXIS instances

Explicit non-goals in the v1 security core

No auth/TLS/RBAC · no production-grade tenant isolation · no external secrets management · no metrics/observability backend · no log rotation or retention policy · no full historical audit-chain verifier · no distributed audit-chain coordination · no production deployment hardening.

Bypass honesty: AXIS cannot protect database traffic that bypasses AXIS entirely. Production deployments must enforce network, IAM, firewall, security-group, and database access controls so protected write paths must pass through AXIS. Hard bypass creates an evidence gap that AXIS cannot retroactively prove closed.

Pilot integration: FastAPI + SQLAlchemy (HTTP adapter model)

The pilot (demo/docker-compose.pilot.yml) uses a realistic business backend. Reads execute directly against PostgreSQL (path: direct_postgres). Protected writes are compiled by SQLAlchemy (AxisRoutingSession) and submitted to AXIS HTTP /query for policy evaluation and execution. This is an application integration model, not a driver-level proxy model.

  • Covered: single-row INSERT/UPDATE, blocked destructive delete (BLOCK, 403), role-change approval flow (REQUIRE_APPROVAL, 202), explicit retry with approval_id after approval, rejection (409), transaction rollback around approval-required and blocked operations.
  • APPROVAL uses rollback + explicit retry: AXIS never holds the database transaction open while waiting for a human. If approved, the original business operation is resubmitted with the approval_id.
  • Not proven: universal SQLAlchemy dialect behavior — arbitrary flush ordering, relationship cascades, custom type binders, stored procedures, server-generated non-primary values, arbitrary bulk parameter sets.
  • ORM-generated SQL: extremely complex or vendor-specific shapes may be rejected or fail closed until profiled into the supported regression corpus. This is intentional: AXIS prefers fail-closed over silently allowing SQL it cannot classify with confidence.
  • Prisma Migrate / schema introspection is out of scope; migrations should use a direct privileged connection unless product requirements change.

Protocol-boundary behavior worth knowing

Fail-closed

  • COPY FROM STDIN / COPY TO STDOUT / CopyData sub-protocol: not supported, rejected before bulk transfer, connection usable after rejection
  • Pipeline mode: rejected (42501 / unsupported_extended_pipeline)
  • Sensitive session GUCs denied: search_path, role, session_authorization, row_security — whitelisting any requires its own bypass analysis
  • Stored routine bodies are opaque: AXIS policies the SQL text sent by the client, not the body of previously created functions/procedures (e.g. SELECT process_order(123) does not reveal an internal DELETE). Regression-covered; complementary control is PostgreSQL native GRANT/REVOKE

Extended Query status

Parameterized single-statement flows are tested with real drivers (Parse/Bind/Execute/Sync). Full Extended Query positive-path support — prepared statement state machines, portals, batch cycles, and ≥4 major driver stacks passing ALLOW/BLOCK/APPROVAL/audit tests without unsafe downgrades (extended-query roadmap acceptance criterion) — is the required gate before a real OLTP pilot. Same-cycle pipelining stays rejected.

05 · Evidence

Audit chain, hash-chain verification, raw evidence standard

Every important decision produces an audit event. The audit WAL is the canonical source of evidence; the JSONL projection is operator convenience; the derived index is a disposable read model. If AXIS claims durable evidence, the evidence format must be explicit. "We logged it somewhere" is not evidence.

What each event records

request_id event_id event_type actor / app / tenant / role / host / env operation classifier sql_fingerprint normalized_sql / raw_sql / params target / scope risk_signals decision / policy_decision reason_code matched_rule policy_version / policy_sha256 previous_hash event_hash

How the hash chain works

  1. Each event carries a previous_hash pointing to the last committed event hash, and an event_hash computed from canonical event content: SHA-256(canonical_json(record_without_event_hash)) (lowercase hex).
  2. On restart, AXIS reads the final non-empty audit record and continues the chain from that hash — the first post-restart previous_hash equals the pre-restart last event_hash (verified by axis_audit_restart_test.py).
  3. GET /evidence/verify and GET /audit/verify recompute event hashes and verify linkage without mutating the log. Verification depth is full_hash (recomputed event hashes), not merely linkage.
  4. Malformed records, missing hash fields, or mismatched hashes are reported as invalid evidence. AXIS does not silently repair evidence.
Current evidence proves restart continuity from the last event into the first post-restart event. It does not yet prove full historical chain verification from the first event to the last event — that remains on the roadmap.

Raw evidence standard (WAL record, native PG spec v1.2)

Each WAL record is one canonical JSON object, UTF-8, \n terminated: no pretty printing, no comments, no trailing commas. Required fields: schema_version (axis.audit.wal.v1), event_id, event_type, event_time_utc, instance_id, session_id, axis_request_id, sequence, previous_event_hash, event_body, event_hash. Hash input is canonical JSON: UTF-8, sorted object keys, no insignificant whitespace, stable number representation, event_hash excluded from its own hash input, previous_event_hash included.

{
  "schema_version": "axis.audit.wal.v1",
  "event_id": "evt_...",
  "event_type": "AXIS_POLICY_EVALUATED",

Dispatch discipline: before forwarding protected execution, AXIS writes AXIS_BACKEND_DISPATCH_INTENT (with intent_durable); blocks record backend_forwarded=false and tcp_bytes_forwarded=0 — an AXIS-layer assertion strengthened by byte-level backend-mock tests, not "magically witnessed by PostgreSQL". AXIS_EXECUTION_UNKNOWN (backend response lost, cannot_confirm_non_execution=true) is distinct from AXIS_BACKEND_CONFIRMED_CLIENT_DELIVERY_UNKNOWN. Raw SQL is not stored by default. Event taxonomy includes connection, startup/auth-observed, query received, policy evaluated, dispatch, block applied, approval issued, safety rollback, execution-unknown, emergency bypass, restart-recovery marker events.

Signed audit WAL and checkpoint anchoring (hardening notes)

The hardened audit path adds: a monotonic sequence_number, Ed25519 key_id, event signature, previous_hash and event_hash on every event; production startup requiring an audit signing key path (AXIS_AUDIT_SIGNING_KEY_PATH); epochs.log recording key epochs for offline verification after rotation; and checkpoint anchoring (axis.audit.checkpoint.v1) that signs the latest durable WAL head and delivers it to an append-only file replica or a webhook with receipts. Verification binaries: cargo run --bin axis-audit-verify -- --epochs epochs.log audit.wal (optionally --checkpoints checkpoints.log). Checkpoint anchor failures never roll back a locally committed WAL event; they retry with bounded exponential backoff and elevate to a hard alert after threshold. Production pg_hba baseline checks (hostssl/cert) are specified with axis-generate-pg-hba and signed AXIS_PG_HBA_DRIFT_DETECTED events — per hardening notes.

Evidence Bundle V1 (portable, share-safe export)

GET /audit/export produces a bundle: bundle_type: axis.evidence_bundle.v1, schema version 1.0, canonicalization axis.canonical_json.v1 (lexicographic keys, RFC3339 timestamps), plus: bundle metadata, the verifier report at export time, active-policy evidence (policy id/version/SHA-256, manifest state), exported events in share-safe summary form, integrity metadata (payload_sha256, event_hashes_sha256 over the ordered non-empty event-hash array, optional Ed25519 signature + signed_at), and redaction posture (secrets_redacted: true, filesystem_paths_redacted: true, raw_fields_included: false). The bundle never includes raw audit records, signing private keys, operator tokens, backend env variables, or filesystem paths.

What a bundle proves: that the included AXIS evidence was exported in a stable V1 structure and has not changed since the recorded hash/signature. It does not prove external business truth — ticket correctness, customer requests, or database state outside AXIS — and cannot prove evidence that was not included. Known limitation: WAL reads are linear; large logs make export/verification latency proportional to WAL size.

Source-of-truth rules

Audit WAL is canonical; the JSONL projection is convenience; the Audit Derived Index V1 is disposable (safe to delete/rebuild, checksummed, never used as proof — /audit/verify always verifies the WAL; exports re-read WAL bodies before hashing). Decision traceability (GET /audit/trace) is read-only and WAL-backed: it never executes SQL, never mutates approval/policy/audit state, and never treats runtime logs as proof. Runtime logs are bounded, in-memory, reset on restart, and are not hash-chain evidence.

06 · Verification

Test methodology: no PASS without raw evidence

AXIS verification has one discipline: a PASS claim requires captured raw evidence — recorded responses, audit files, byte-level mock captures, or verifier outputs. A demo claim without evidence files is a failure. This section describes the current baseline and how it is reproduced.

Principle: raw evidence, not narrative

  • The pilot evidence package is captured by scripts/capture_pilot_evidence.py from a running stack over HTTP — it never fabricates policy decisions, approval ids, audit ids, or placeholder screenshots. A partial capture leaves PARTIAL_CAPTURE.txt, which the verifier treats as failure.
  • scripts/verify_pilot_evidence.py prints PILOT_EVIDENCE_VERIFICATION: PASS or FAIL with the exact missing file/field. "PASS" means the evidence directory is complete and internally consistent for the current pilot claim.
  • Byte-level discipline (native pgwire): PostgreSQL logs are not proof that a blocked query never reached the backend — logging can be wrong, and absence in logs is not absence on the wire. A byte-level backend mock records the exact bytes AXIS wrote; BLOCK / APPROVAL_REQUIRED / unsupported-COPY paths must record zero original query bytes, ALLOW must forward bytes unchanged.
  • Mutation tests (Security Classification Contract v1.0, §5.4): for at least one critical detection (e.g. IntoClause / SELECT INTO), disable the detection logic → the corresponding test must FAIL (red); restore → PASS (green). CI must break if mutation tests pass while detection logic is disabled. The contract also requires: a positive test per mandatory write pattern, a negative test per pure read pattern, override tests for SELECT INTO and CTE writes, and CI failure when a newly added SQL construct has no test.
  • The claims matrix maps every reviewer-package claim to concrete evidence files, verification commands, and explicit limitations. "If a claim is not listed there, assume it is not claimed by this package."

Documented named limits (regression-covered where noted)

  • Stored function/procedure bodies are opaque to wire-level policy (architectural limit for any proxy at the PostgreSQL wire layer; complementary control: native GRANT/REVOKE).
  • COPY protocol not supported in pgwire mode; fail-closed before bulk transfer.
  • Sensitive session GUCs (search_path, role, session_authorization, row_security) permanently denied in pgwire mode.
  • Direct database bypass: AXIS cannot protect traffic that never reaches it; network/IAM/firewall controls are the operator's responsibility.
  • The current pilot is an HTTP adapter integration, not a transparent driver-level proxy; HTTP demo mode passing does not prove native wire coverage.
  • Audit durability in real deployments additionally depends on disk reliability, volume config, backup, retention, monitoring, and access controls around evidence storage.
  • Single-node AXIS deployment is not an HA architecture; audit index is a single JSON file; no enterprise observability pipeline.
  • Cancellation: registry is memory-only — AXIS restart invalidates all proxy cancel keys; 24-hour TTL per key; multi-instance requires shared protected cancel state.
  • JWT HS256 demo mode is not enterprise IAM (no rotation, revocation, centralized access audit); SHA-256 manifest validation is local file integrity, not asymmetric signing.
08 · Roadmap

Next priorities (as ordered by the RFCs and changelogs)

These items come from the native-PG integration RFC v1.2 production gate, the extended-query roadmap, CancelRequest follow-up work, the audit scaling plan, and the pilot next-steps notes. They are ordered by the gates the RFCs require before production claims.

Gate 1 — before any real OLTP pilot

Extended Query production support

Full Parse/Bind/Execute/Sync positive-path support with prepared statement state machines and portals; phases EQ-0…EQ-5 (discovery → parse tracking → bind tracking → execute → sync/error recovery → driver compatibility). Acceptance: at least four major driver stacks pass ALLOW/BLOCK/APPROVAL/audit tests without unsafe downgrades (targets: psycopg3, asyncpg, node-postgres, Prisma, JDBC/Hibernate, Npgsql, Go pgx, SQLAlchemy). Not optional — most serious production stacks use prepared statements.

Gate 2 — transport

Production TLS/mTLS on pgwire

Replace the temporary trusted-network boundary (RFC-032 Scenario A) with one shared backend connector for normal sessions and CancelRequest, certificate and server-name validation, and a consistent TLS requirement on both paths; measure handshake latency before setting the cancel timeout. Client-to-proxy mTLS termination is the preferred enterprise target (mapping cert identity to actor/service identity), with SCRAM strategy and OIDC/LDAP evaluation.

Gate 3 — state

Approval store HA; identity — verified not claimed

Approval store technology and HA posture are undecided in RFC v1.2 and must be selected before multi-AXIS pilots; split-brain must fail closed. Identity work: verified approver and caller identity (mTLS, OIDC/JWKS, KMS), with audit evidence that states which identity was verified vs merely observed.

Gate 4 — evidence

External witnessing + full-chain verification

Publish Merkle roots or head hashes to an external witness (customer-controlled object store, timestamping service, signed transparency log, append-only external ledger) to reduce the "you wrote logs after the fact" objection; implement full historical hash-chain verification; signed bundles mandatory for attribution.

Operability

Audit ops: sealing, retention, rotation

Sealed WAL segments plus segment indexes (linear WAL reads today), asynchronous index rebuild, retention/compaction/archival with integrity verification before deletion, legal hold, low-watermark alerts, log rotation, and on-call dashboards. Emergency bypass gains a fixed audit-only mode and the reconciliation procedure from RFC-029 (append AXIS_BYPASS_RECONCILIATION_COMPLETED, unverified operations marked, never silently hidden).

Measurement

Controlled benchmarks; second-stack pilot

Performance measured with defined hardware, dataset shape, workload, warmup, repetitions and methodology — separate ALLOW-path latency from enforcement-only decision latency, exclude human approval time. Build a Java/Spring Boot + Hibernate demo to test whether policy, approval, rollback and audit concepts transfer beyond Python/SQLAlchemy; validate PgBouncer session pooling with server_reset_query semantics.

Post-gate

Production pilot checklist

Narrow protected write path, defined policy pack, known schema, agreed rollback/incident procedure, operator ownership (who changes policy, who decides in incidents), log retention expectations, evidence review agreement, and customer environment mapping — then the RFC v1.2 verdict applies: v1.2 is sufficient to guide a disciplined Simple Query lab PoC; it is not sufficient to claim production readiness.

The RFC v1.2 production gate must be read literally: a real production pilot must not start until Extended Query is implemented and tested for the target driver stack, CancelRequest is implemented or explicitly disabled with customer acceptance, the audit WAL format and verification are stable, approval-store HA posture is defined, identity attribution is accepted, PgBouncer mode is validated, performance and durability modes are chosen, the emergency bypass procedure is rehearsed, and observability dashboards and on-call runbooks exist.
